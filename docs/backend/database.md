# Database

---

## Engine and file location

coco-iam uses **SQLite** as its database engine via the `mattn/go-sqlite3` driver. SQLite was chosen for its zero-configuration deployment model: no separate database server process is required.

The database file is located at:

```
./data/db/users.db
```

The `data/db/` directory is created automatically on first startup if it does not exist. The path is relative to the working directory from which the binary or `go run` is invoked, which is normally the project root.

## Schema

### `migrations`

Managed internally by coco-orm. Records which SQL migration files have been applied.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY | The filename of the applied migration (e.g. `15_02_2026_12_21_22.sql`) |
| `created_at` | DATETIME | NOT NULL | UTC timestamp of when the migration was applied |

---

### `admin_users`

Stores administrator accounts that can log in to the coco-iam admin interface.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY, UNIQUE, NOT NULL | UUID v4 generated by coco-orm |
| `username` | TEXT | NOT NULL | Login username; indexed |
| `email` | TEXT | NOT NULL | User email address; indexed |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `limited_access` | BOOLEAN | NOT NULL, DEFAULT TRUE | Reserved flag; not currently used by IAM logic |
| `is_super_admin` | BOOLEAN | NOT NULL, DEFAULT FALSE | When true, the user's token includes the `super:admin` scope and all scope checks pass |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Soft-delete flag; inactive users cannot log in |

Indexes: `admin_users_id_index`, `admin_users_email_index`, `admin_users_username_index`, `admin_users_is_active_index`.

---

### `user_auth_password`

Stores bcrypt-hashed passwords for admin users. Separated from `admin_users` so that password data is never accidentally included in user query results.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `user_id` | TEXT | PRIMARY KEY, UNIQUE, NOT NULL | Foreign key to `admin_users.id` |
| `password` | TEXT | | bcrypt hash of the user's password |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Allows a password record to be deactivated without deletion |

Index: `user_auth_password_user_id_uindex` (unique on `user_id`).

---

### `user_acl`

Stores access control lists assigned directly to individual admin users.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY, UNIQUE, NOT NULL | UUID v4 |
| `user_id` | TEXT | NOT NULL | Foreign key to `admin_users.id`; unique index enforces one ACL record per user |
| `roles` | JSON | NOT NULL | JSON array of scope strings (e.g. `["admin:users:read", "admin:groups:read"]`) |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Inactive records are excluded from scope resolution |

Indexes: `user_acl_id_index`, `user_acl_user_id_uindex` (unique on `user_id`).

---

### `user_groups`

Defines admin groups. A group is a named collection of users that can be assigned a shared set of scopes via `user_group_acl`.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY, UNIQUE, NOT NULL | UUID v4 |
| `group_type` | TEXT | NOT NULL | Discriminator value; always `"admin"` for admin groups managed by coco-iam |
| `title` | TEXT | NOT NULL | Human-readable group name |
| `group_description` | TEXT | DEFAULT `''` | Optional description of the group's purpose |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Inactive groups are excluded from scope resolution |

Indexes: `user_groups_id_index`, `user_groups_user_id_uindex` (unique on `id`), `user_groups_is_active_index` (on `title`).

---

### `user_group_members`

Join table linking admin users to groups. A user can be a member of multiple groups.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY, UNIQUE, NOT NULL | UUID v4 |
| `user_id` | TEXT | NOT NULL | Foreign key to `admin_users.id` |
| `group_id` | TEXT | NOT NULL | Foreign key to `user_groups.id` |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Inactive memberships are excluded from scope resolution |

Indexes: `user_group_members_id_index`, `user_group_members_group_id_index`, `user_group_members_user_id_index`, `user_group_members_user_id_group_id_index`, `user_group_members_user_id_group_id_uindex` (unique composite on `user_id, group_id`).

---

### `user_group_acl`

Stores access control lists assigned to groups. When a user is a member of a group, all scopes in that group's ACL are included in the user's effective scope set at login time.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY, UNIQUE, NOT NULL | UUID v4 |
| `group_id` | TEXT | NOT NULL | Foreign key to `user_groups.id`; unique index enforces one ACL record per group |
| `roles` | JSON | NOT NULL | JSON array of scope strings |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Inactive records are excluded from scope resolution |

Indexes: `user_group_acl_id_index`, `user_group_acl_group_id_uindex` (unique on `group_id`).

### `organization`

Stores top-level organisation records. Used for multi-tenant workspace organisation.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY, UNIQUE, NOT NULL | UUID |
| `title` | TEXT | NOT NULL | Organisation name |
| `description` | TEXT | | Optional description |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Soft-delete flag |

### `workspace`

Stores workspace definitions. A workspace can be linked to multiple organisations via the `workspace_organizations` join table (many-to-many, no owner).

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY, NOT NULL | UUID |
| `title` | TEXT | NOT NULL | Workspace name |
| `description` | TEXT | Nullable | Optional workspace description |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Soft-delete flag |

Index: `workspace_id_index`.

All schema setup lives in a single consolidated migration file `15_02_2026_12_21_22.sql`. The workspace table has no `organization_id` column — org links are held in the `workspace_organizations` join table. The `description` column is nullable.

---

### `workspace_organizations`

Join table implementing the many-to-many relationship between workspaces and organizations.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY, UNIQUE, NOT NULL | UUID |
| `workspace_id` | TEXT | NOT NULL | References `workspace.id` (no DB-level FK) |
| `organization_id` | TEXT | NOT NULL | References `organization.id` (no DB-level FK) |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Soft-delete flag |

Indexes:
- `workspace_organizations_unique_idx` (UNIQUE on `(workspace_id, organization_id)` — prevents duplicate memberships)
- `workspace_organizations_workspace_id_idx`
- `workspace_organizations_organization_id_idx`

### `users`

Stores regular (non-admin) user accounts belonging to an organisation.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY, UNIQUE, NOT NULL | UUID |
| `username` | TEXT | NOT NULL | Username |
| `email` | TEXT | NOT NULL | Email address |
| `organization_id` | TEXT | NOT NULL | Foreign key to `organization.id` |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Row creation timestamp |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Soft-delete flag |

Indexes: `users_id_index`, `users_email_index`, `users_username_index`, `users_is_active_index`.

## How migrations work

### Storage

Migration SQL files are stored in `api/config/db/migrations/` and are compiled into the binary at build time via `go:embed` in `api/config/embed.go`:

```go
//go:embed routes/** db/migrations/** config.json scopes/**
var ConfigFS embed.FS
```

This means the binary is fully self-contained; no external migration files are needed at runtime.

### Execution on startup

During the `start` action in `main.go`, the following sequence occurs:

1. `config.ExtractMigrationsToTemp()` reads all `.sql` files from the embedded filesystem and writes them to a temporary directory on disk. This is necessary because coco-orm's migration runner expects a filesystem path.
2. `dbmanager.NewDatabaseManager("users.db", "./data/db", []string{migrationsPath})` creates the database manager, pointing it at the temporary directory.
3. `dbInstall.Install(manager)` calls `manager.SyncMigrations()`.

### Migration tracking

`SyncMigrations` (in `coco-orm`) maintains a `migrations` table. For each `.sql` file in the migration directory:
- It checks whether a row with that filename already exists in the `migrations` table.
- If the file has not been applied, it executes the SQL and records the filename and current timestamp.
- If the file has already been applied, it is skipped.

Migration files are processed in the order returned by `os.ReadDir`, which is alphabetical. File names are timestamp-based (e.g. `15_02_2026_12_21_22.sql`) to guarantee a consistent and predictable execution order.

Migrations are **not reversible**. There is no down-migration mechanism. Schema changes that need to be reverted must be addressed by a new migration file.

### SQL file format

Statements within a migration file are delimited by `/***Statement***/` on its own line. This allows multi-line statements (including `CREATE TABLE` with constraints) to be written naturally without worrying about semicolons inside statement bodies.

```sql
/***Statement***/
CREATE TABLE example (
    id TEXT NOT NULL PRIMARY KEY
);
/***Statement***/
CREATE INDEX example_id_index ON example (id);
```

## coco-orm usage pattern

coco-orm is the internal ORM library vendored at `api/vendor/github.com/a-digi/coco-orm/`. It is not a general-purpose ORM; it is purpose-built for coco-iam's SQLite-backed data layer.

### DatabaseManager

All database access goes through `orm.DatabaseManager`, which is created once in `main.go` and injected into every handler via `ContextBag`. The manager exposes:

- `QueryBuilder()` — returns a `*QueryBuilder` for constructing parameterised SELECT queries
- `Insert(query, args...)` — executes an INSERT statement
- `GenerateUuidV4()` — generates a new UUID v4 string for use as a primary key
- `Hydrator.HydrateRows(rows, &slice)` — maps `*sql.Rows` into a slice of structs using `db` struct tags
- `SyncMigrations()` — applies pending migrations

### Struct tag conventions

Entity structs use struct tags to describe their database mapping:

| Tag | Example | Purpose |
|-----|---------|---------|
| `table` (on blank field) | `` `table:"admin_users"` `` | Identifies the target table |
| `db` | `` `db:"user_id"` `` | Column name |
| `dbtype` | `` `dbtype:"UUID"` `` | SQL data type; used by the INSERT query builder |
| `nullable` | `` `nullable:"false"` `` | Whether the column accepts NULL |
| `default` | `` `default:"true"` `` | Default value used when the field is zero |
| `discriminatory` | `` `discriminatory:"admin"` `` | Fixed value injected into WHERE clauses for single-table inheritance |
| `relation` | `` `relation:"m2o"` `` | Defines a many-to-one or many-to-many eager load |

### Query pattern (read)

Repositories in `repository/query/` build queries using the fluent `QueryBuilder`:

```go
qb := manager.QueryBuilder().
    Select("id", "username", "email").
    From("admin_users").
    Where("is_active = ?", true).
    Limit(10)

query := qb.Build()
rows, err := manager.Connector.DB.Query(query.SQL, query.Args...)
manager.Hydrator.HydrateRows(rows, &results)
```

### Insert pattern (write)

Repositories in `repository/persistent/` use `InsertObjectQueryBuilder` to derive the INSERT statement from the entity's struct tags:

```go
builder := &orm.InsertObjectQueryBuilder{}
query, args, err := builder.BuildFrom(entity)
manager.Insert(query, args...)
```

The builder inspects each field's `db` and `dbtype` tags, skips fields with empty values where appropriate, and generates a parameterised INSERT statement.

## Adding a new migration

1. Create a new `.sql` file in `api/config/db/migrations/`. Name it using the current date and time in the format `DD_MM_YYYY_HH_MM_SS.sql` to ensure it sorts after all existing migrations.

2. Write each SQL statement preceded by the delimiter:

    ```sql
    /***Statement***/
    ALTER TABLE widgets ADD COLUMN description TEXT;
    /***Statement***/
    CREATE INDEX widgets_description_index ON widgets (description);
    ```

3. Rebuild the binary so the new file is embedded:

    ```sh
    make build
    ```

4. On the next server start, `SyncMigrations` will detect the new file, execute all statements within it, and record it in the `migrations` table.

The migration will also be applied the next time `make run-dev` or `make run-dev-app` is used, because those targets run `go run main.go start` which triggers the same migration path.
